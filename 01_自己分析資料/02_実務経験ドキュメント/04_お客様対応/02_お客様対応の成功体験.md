### ＜ 1 ＞ 意思決定の支援


 * 【事象】

    - API 連携ツールの開発において、プログラムや API に詳しくないお客様から要望を伺い、  
      仕様を整理しながらプロジェクトを進める必要があった。


 * 【課題】

    - 専門用語や文章だけで説明すると、お客様が完成後の動作をイメージしにくく、  
      仕様に対する認識の相違が発生する可能性があった。

    - お客様自身で詳細な仕様を決めることが難しく、優先度、納期、品質、コストなどを考慮したうえで、  
      意思決定に必要な情報を分かりやすく提示する必要があった。


 * 【取り組み】

    - 業務フロー図や画面イメージを使用し、専門用語をできるだけ避けながら説明した。

    - 意思決定が必要な内容については、複数の対応案と、それぞれのメリット・デメリット、納期・品質・コストへの影響を比較できる資料を作成した。

    - お客様の優先事項を確認しながら各案を説明し、意思決定に必要な情報を整理して提示した。

    - 打ち合わせ後には、決定事項、未決事項、今後の対応事項を整理し、担当者と期限を明確にしたうえで関係者へ共有した。


 * 【結果】

    - 入力値を整数として扱う認識になっていた項目について、小数点以下を含める必要があることを開発前に確認でき、  
      仕様の認識相違と手戻りを防止した。

    - お客様と仕様に対する認識を合わせながら、API 連携ツールの開発を完遂できた。

    - お客様から、仕様が分からなくても画面や資料を見ながら詳細な依頼内容を判断でき、  
      複数の案も整理してもらえるため助かると評価していただいた。


 * 【学び】

    - お客様の IT 知識に合わせて説明方法を工夫し、視覚的な資料や複数の選択肢とそれぞれの影響を提示することが、仕様への理解、円滑な意思決定、認識相違の防止につながると学んだ。

### ＜ 2 ＞ 根本的な課題解決


 * 【事象】

   - 以前のベンダーから引き継いだ SQL を使用する処理について、お客様からダウンロードファイルの形式変更を依頼された。


 * 【課題】

   - 依頼内容の聞き取りだけでは、お客様が本当に解決したい課題が把握できなかった。

   - 対象の SQL は引継ぎ元のベンダーが開発しており、詳細な処理内容を把握できていなかった。


 * 【取り組み】

   - 依頼の背景を確認したところ、ダウンロード処理に約 1 分かかることを改善したいとのことだった。

   - 処理の仕組みを踏まえると、ファイル形式の変更だけでは処理時間の大幅な短縮は見込みにくいと考え、  
     まず SQL の処理内容を調査することを提案した。

   - SQL の処理内容を調査した結果、不要な処理や効率の低いテーブル結合を確認した。

   - 不要な処理を削除し、テーブルの結合方法を適切な形へ変更した。


 * 【結果】

   - ダウンロード処理の時間を約 1 分から数秒まで短縮できた。

   - ファイル形式を変更せずに課題を解決し、変更に必要と見込まれる約 2 人日の作業を削減できた。

   - お客様から、ストレスなくダウンロードできるようになったとの感謝の言葉をいただき、対応への信頼にもつながった。


 * 【学び】

   - 依頼された内容をそのまま実施するのではなく、依頼の背景やお客様が実現したいことを確認し、  
     根本的な課題に対する解決策を提案することが重要だと学んだ。

   - 依頼内容に技術的な懸念がある場合は、そのままにせず、お客様へ伝えたうえで、  
     必要な調査を提案することが重要だと学んだ。
